````md
## 📌 Описание проекта

**SpreadScope** — веб-приложение для мониторинга спредов между криптовалютными биржами и конвертации активов.  
Система реализована в виде клиент-серверного приложения:

- Backend: FastAPI (Python)
- Frontend: HTML / CSS / JavaScript
- Источники данных: API бирж (Gate, MEXC, Ourbit)
- Хранение данных: in-memory (на этапе MVP)

---

# 🧠 1. Что такое технический долг

Технический долг — это накопленные недостатки архитектуры, кода и процессов разработки, которые:

- замедляют разработку
- увеличивают вероятность ошибок
- усложняют поддержку системы

К признакам технического долга относятся:

- нечитаемый код  
- дублирование логики  
- отсутствие тестов  
- запутанная архитектура  
- отсутствие автоматизации  
- отсутствие документации

# 🔍 2. Анализ проекта на наличие технического долга

В ходе анализа проекта SpreadScope были выявлены следующие признаки технического долга:

---

## 🔴 2.1 Высокая связность компонентов (God-object)

**Файл:** `backend/app.py`

### Проблема:
- В одном файле объединены:
  - API endpoints
  - бизнес-логика
  - polling бирж
  - WebSocket
  - работа с данными

### Последствия:
- сложно поддерживать
- сложно тестировать
- трудно расширять

---

## 🔴 2.2 Отсутствие слоя репозиториев

### Проблема:
- данные хранятся в:
  ```python
  PRICES = {}
  META = {}


* нет абстракции доступа к данным

### Последствия:

* невозможно легко заменить хранилище (например, на БД)
* логика зависит от структуры данных

---

## 🔴 2.3 Использование in-memory хранения

### Проблема:

* все данные хранятся в памяти процесса

### Последствия:

* данные теряются при перезапуске
* невозможно масштабирование

---

## 🔴 2.4 Неполное разделение бизнес-логики

### Проблема:

* часть логики находится в сервисах (`spreads.py`)
* часть — прямо в `app.py`

### Последствия:

* нарушение принципа разделения ответственности
* ухудшение читаемости

---

## 🔴 2.5 Отсутствие CI/CD

### Проблема:

* тесты есть, но запускаются вручную

### Последствия:

* возможен коммит с ошибками
* нет автоматической проверки

---

## 🔴 2.6 Отсутствие системы авторизации

### Проблема:

* отсутствует user management

### Последствия:

* невозможность реализации персональных функций (избранное, история)

---

## 🔴 2.7 Упрощённая архитектура frontend

### Проблема:

* весь код в одном файле (`app.js`)
* отсутствует структура компонентов

### Последствия:

* сложно масштабировать
* сложно добавлять новые функции

---

# 🛠 3. План устранения технического долга
````
